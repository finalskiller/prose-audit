# 文镜 · 语言审查（prose-audit）

> 好文字不是写出来的，是删出来、读出来、再改出来的。

一个给大模型用的中文写作质检技能（skill）。它审的不是错别字，是**让读者替作者干活**的那类毛病：读者得自己补主语、破译速记、拆开堆叠的定语、跳过废话、读到最后才知道要干什么。

「说人话」的定义是**让人一遍读懂**，不是把话说得更口语。一段很正式但一次读懂的话，是合格的。

---

## 它治什么

| 病 | 长相 |
|---|---|
| 过度缩写 | `环境配一下，跑通就行。`——谁配、配到什么程度 |
| 内部速记 | `按 T1 的方案执行`——编号只有作者知道 |
| 缺主谓短句 | `已确认。`——上一段有五个待确认项，读者不知道确认了哪个 |
| 术语堆叠 | `基于多模态大模型的端到端一体化智能体编排框架` |
| 冗余重复 | `非常关键且重要`、`总的来说，整体上…` |
| 机械化表达 | `首先…其次…最后…`——换个主题照样成立 |
| 结论埋没 / 漏答 | 500 字读完才看到"先别上线"；或者根本没回答用户问的 |

---

## 两种模式

| 模式 | 触发词 | 产出 |
|---|---|---|
| **审稿** | 语言审查、审一下这段话、有没有 AI 味、读起来别扭 | 8 维评分 + 缺陷清单 + 回炉后的终稿 |
| **标注** | 标注、划一下、span、对比两份回复、内容质量低 | JSON：逐字 span + 标签 + 理由 + 改法 + 修正回复 |

审稿模式下，`总分 ≥90 且 重度缺陷 = 0 且三条红线全过`才放行；88–92 分复评一次取低分；不过就回炉改写，默认最多 4 轮。

**DeepSeek Harness（用户级，所有会话可用）**

```powershell
git clone https://github.com/finalskiller/prose-audit "$env:USERPROFILE\.dsh\skills\prose-audit"
```

**项目级**：把目录放进 `<项目根>/.dsh/skills/prose-audit/`，只在该项目生效。

**其他 agent**：把 `SKILL.md` 作为系统提示的一部分，或让模型在需要时读它。`references/` 按需加载，不必一次塞进上下文。

依赖：Python 3.9+（只有两个可选脚本需要，没有也不影响审查）。

## 用法

审稿：

```
语言审查一下这段话：<你的稿子>
```

标注（需要先把两份回复整理成 payload）：

```powershell
python scripts\annotate_check.py --payload payload.json --candidates   # 先看候选锚点
# ……模型产出 answer.json 后……
python scripts\annotate_check.py --payload payload.json --answer answer.json
```

`payload.json`：

```json
{"context": "对话上下文", "replies": {"1": "模型1的回复", "2": "模型2的回复"}}
```

候选锚点只是核对清单，不是答案。真正伤读者的语义病（指代、限定、跳步、自然语速记）机器给不了。

## 评分卡

| # | 维度 | 权重 | 抓什么 |
|---|---|---|---|
| 1 | 完整度 | 18 | 句子成型、结论位置 |
| 2 | 明白度 | 18 | 解码成本：缩写、速记、堆叠 |
| 3 | 精确度 | 12 | 指代与限定是否唯一 |
| 4 | 简洁度 | 12 | 有没有多余的字 |
| 5 | 语感 | 14 | 像人写的，还是模板拼的 |
| 6 | 得体度 | 10 | 对不对人、对不对场合 |
| 7 | 格式 | 10 | 标点、空格、层级 |
| 8 | 一致性 | 6 | 术语前后统一 |

扣分制：重度 −6 / 中度 −3 / 轻度 −1；**一句只记一类**，取最重；同一类全文 ≥3 处额外扣 3 分、**不升重度**。

### 三条硬红线

1. **保真**：不新增事实、数字、承诺；不删限定条件。
2. **意图**：不改变立场和承诺强度；不把口语和书面语混写。
3. **克制**：不为通顺牺牲术语，也不把口语改写成官样文章。

红线破一条，本轮直接不通过，无论总分多少。

### 为什么是"90 分 + 重度 = 0"

分数是门禁，不是 KPI。一条重度缺陷——读者会误解、或不知道谁做什么——不会因为整体流畅就被原谅。所以 `重度 = 0` 才是真正的验收线。

## 设计取舍

- **扣分制，不是印象分**：每一分都要能指回原文某一句。指不到就不扣。
- **脚本只数数，模型判断**：`audit_metrics.py` 出句长、重复短语、套话、标点、混排信号，不给分。判断归人。
- **先打分再改**：改写者一旦动笔，就会倾向于证明自己改得对。
- **封存清单**：下一轮审稿先不看上一轮的缺陷清单，重新冷读。照着清单打钩，永远能打出 90 分。
- **达标即停**：首轮 ≥90 就直接交付原文。已经合格的稿子，动一刀就多一分改坏的风险。
- **退化回滚**：新分比上一版低 5 分以上，回滚并降一档幅度。过度润色本身就是一种机械化。

## 已验证 / 未验证

诚实地说清楚：

- 审稿模式做过 3 轮盲评 A/B（对比不同版本的规则），最后只保留了被验证有效的改动。
- 标注模式的判据就是审稿那套 D1–D12，没有独立验证；`annotate_check.py` 做过 9 类注入错误的自测，全部命中。
- 稳定性这块有个负面结论：给标注流程加"候选锚点 + 分步清单"并没有让 span 更稳（Dice 0.78 vs 0.80），所以本仓库只保留了契约和校验器，没有把那套流程塞进来。
- 没在真实业务语料上大规模跑过。样本都是构造的。
